# 架构与生命周期

当前库保留单一 WPF 程序集。管理器、展示宿主、通知控件和内部状态组件的划分适合现有规模；这些组件之间存在明确的 WPF Dispatcher 和视觉树依赖，因此没有增加独立服务容器或额外项目。

| 组件 | 职责 |
| --- | --- |
| `NotificationManager` | 校验请求、选择目标、协调标签去重和管理器释放 |
| `NotificationHandle` | 提供单条通知操作；在通知的 Dispatcher 内检查状态并更新内容 |
| `NotificationOverlayHost` | 管理每个屏幕的窗口、创建失败回滚和窗口回收 |
| `NotificationArea` | 管理容器、排列、溢出和可选卸载清理 |
| `Notification` | 控件外观、交互、关闭状态和生命周期完成 |
| `NotificationExpirationTimer` | UI 线程上的定时、暂停、恢复和取消状态 |
| `NotificationStore` | 活动句柄与标签索引；锁保护后台完成回调对索引的访问 |

## 关键约束

- 显示、内容更新和关闭都在目标 Dispatcher 上执行。检查是否已关闭与更新内容处于同一个 Dispatcher 回调。
- 取消回调只投递 UI 操作，不同步等待 UI 线程。回调绑定原调度的完成对象，旧取消不能结束新调度。任务正常结束前清除取消调度的剩余时间、截止时间与回调引用。
- 关闭任务在触发公开事件前创建，防止事件处理器重入关闭。内部宿主移除通过独立通知完成，公开事件的异常或 `Handled` 标志不会跳过清理。关闭事件抛异常会使 `CloseAsync` 失败，句柄 `Completion` 仍提供关闭原因。
- 已关闭的 `Notification` 不可重新显示；创建新控件实例。更新普通内容可复用活动句柄。
- Overlay 创建和失败回收由同一个宿主管理。替换目标显示失败时，不主动关闭原有同标签通知；成功插入仍遵守区域的溢出策略。
- `DisposeAsync()` 在 UI Dispatcher 退出前等待通知关闭，然后回收 Overlay。`Dispose()` 只发起清理。
- `ClearOnUnload` 默认关闭，保留临时卸载/重挂行为。页面生命周期需要卸载即清理时显式开启。长期存活的管理器与永久通知需有明确拥有者负责释放。
- 模板选择根据每次调用的资源范围解析，不在共享选择器中缓存某个窗口的模板。

## 验证与后续边界

SDK 由仓库 `global.json` 选择稳定 .NET 10，同一功能带内允许补丁更新；CI 从项目读取包版本。

回归测试覆盖取消/重排、关闭重入、事件异常、跨线程更新、Overlay 失败回收、替换失败保留、模板资源范围和卸载策略。真机混合 DPI、任务栏工作区变化与读屏效果仍按 `UI-ACCEPTANCE.md` 验收。屏幕选择是动态的：`ClearAsync` 按调用时的鼠标/拥有者所在屏幕清理；关闭某条既有通知应使用它的句柄。
